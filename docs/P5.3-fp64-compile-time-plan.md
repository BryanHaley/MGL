# P5.3 — fp64 compile time and the enhanced_layouts full run

Research/documentation only. No source changes. Prepared 26 Sep 2026.

Everything below is read from the tree and the roadmap; the only number
actually *measured* is the roadmap's ~30 s per 64-bit shader. No new Metal
timings were taken for this note (see "Uncertainties").

---

## 1. Does a Metal library cache exist, and how does it work?

**Yes — one, in memory, per renderer.** There is no on-disk cache and no
`MTLBinaryArchive` anywhere in the tree.

### The in-memory cache

`src/MGLRenderer.m`:

- `MGLRenderer.m:293` — the ivar:
  `NSMutableDictionary<NSString *, id<MTLLibrary>> *_libraryCache;`
  Comment at :292: *"one MTLLibrary per distinct MSL source, so the same
  shader is compiled once"*.
- `MGLRenderer.m:4647` — `- (id<MTLLibrary>) compileShader:(const char *) str`
  is the single choke point. Every stage goes through it
  (`:4706` `buildStageFunction:`, `:4792` `bindMTLProgram:`, `:5740` the
  clear shader).
- `:4674-4675` — lazily created on first compile.
- `:4677-4680` — **cache lookup keyed on the MSL source string**; a hit
  returns the existing `MTLLibrary` and skips `newLibraryWithSource:`.
- `:4682` — miss: `[_device newLibraryWithSource: source options: opts error: &error]`.
  `opts` is built at `:4654-4664` with `MTLMathModeSafe` (macOS 15+) /
  `fastMathEnabled = NO`, i.e. the options fp64 needs.
- `:4691-4692` — **eviction is crude**: `if (_libraryCache.count > 512)
  [_libraryCache removeAllObjects];` — the whole dictionary is emptied the
  moment it exceeds 512 entries.
- `:4694` — insert.

### Lifecycle and scope

- The cache is an instance variable on the renderer object. glcts builds one
  context and runs every case in one process, so the cache **persists across
  cases within a single sweep** — but only for sources that literally repeat.
- It does **not** survive process exit. A separate "pre-warm" process cannot
  seed it.
- It is **not** keyed on a hash; the full MSL source string is the key
  (correct, just memory-heavy).

### Why the cache cannot fix the fp64 problem

The 30 s is paid **per distinct fp64 shader**. `enhanced_layouts` cases each
build their own shaders, so distinct sources dominate; a per-source-string
cache has almost nothing to reuse across 4,250 cases. The cache's real value
is avoiding a *second* compile of the same stage inside one program build
(`buildStageFunction:` and `bindMTLProgram:` both call `compileShader:`), and
it is working for fp64 exactly as for any other shader — same code path, same
options. So P5.3 option (a) ("already partially done — verify it works for
fp64") is **verified present and correct, but it is not the lever that moves
the sweep time**.

Two cache-related risks worth naming:

- The 512-entry flush means that in a long sweep a source compiled early can
  be evicted and, if requested again later, recompiled at full 30 s cost.
  An LRU (or a much larger cap) would remove that multiplier. This is a
  source change, not requested here.
- The roadmap (line 864) records that Metal keeps one compiled copy behind
  however many `MTLLibrary` objects exist; the cache was introduced to stop
  over-release, not for speed.

## 2. Estimated time for the full enhanced_layouts run

Roadmap figures (`.llminal/docs/MGL-4.6-Critical-Path.html`):

- **4,250 cases** in the group (line 961).
- **2,057** of them carry 64-bit types (line 387).
- **~30 s** per 64-bit shader in Metal's compiler (line 387), because the
  triple-float emulation produces very large MSL — the captured samples are
  `build/cts-work/p53/dbl.msl` (107 KB) and `big.msl` (110 KB) against
  `plain.msl` (1 KB) for the same shader without doubles.

Arithmetic:

| Component | Cases | Rate | Time |
|---|---|---|---|
| fp64 cases, 1 shader each | 2,057 | 30 s | **61,710 s ≈ 17.1 h** |
| remaining cases (fast) | 2,193 | ~1–2 s | ~0.6–1.2 h |
| **Total (1 fp64 shader/case)** | 4,250 | | **≈ 17.5–18.5 h** |

The roadmap's own statement (line 387) is *"the group alone is about
seventeen hours"*, which matches.

**Sensitivity:** 30 s is per *shader*, and a case can carry more than one fp64
stage (vertex + fragment, or + tessellation/geometry). At 1.5 fp64 shaders per
fp64 case the same arithmetic gives **≈ 25.7 h**, i.e. over 24 h. So the
answer to "does it fit in 24 hours?" is **17 h if one fp64 shader per case,
~26 h if 1.5** — it straddles the P5.3 done-when boundary. This is the single
number that needs measuring (see §5).

## 3. Is the 608-case sample sufficient?

Roadmap's position (three separate statements):

- Line 313: *"for KHR-Single-GL46 the whole of arrays_of_arrays_gl plus the
  fixed 608-case enhanced_layouts sample Tier 2 was measured on."*
- Line 348: *"enhanced_layouts, the 608-case sample … 561→570 / 608"*.
- Line 387: *"The 608-case sample stands in for it here, and compile time for
  fp64 shaders is now a performance item, not only a correctness one."*
- Line 973: the sample is *"608 cases, one in seven, the same list before and
  after"* — a fixed, stratified, before/after list (4250/7 ≈ 607).

Three different lists appear in the document; they are distinct:

1. **180-case triage probe** (line 961) — two cases per family prefix, 108
   prefixes; used once to attribute causes by message. The document later
   withdraws its conclusion (line 973) because a two-case probe cannot measure
   a 204-case family.
2. **213-case list** (lines 177, 205) — the KHR-Single measurement list,
   198 passing; this is the one behind "15 left" in tier item 15.
3. **608-case fixed sample** (lines 313, 348, 973) — one in seven, the same
   list before and after; this is the stand-in for the full group.

**Verdict:** the 608-case sample is **sufficient for the burndown and for
before/after measurement** — the roadmap already uses it as exactly that, and
line 973 shows it is trustworthy where the 180-case probe was not. It is
**not** sufficient for the final submission figure: the roadmap is explicit
(lines 177, 222, tier item 29 = "half") that because the full group has not
run there is *"no honest both-package total yet"*, and P5.4's done-when asks
that enhanced_layouts pass *every* case outside the waiver list. So: keep the
sample as the published measurement; the full run is still owed for the final
count.

## 4. Do the sweep scripts need a timeout extension?

**No — there is no timeout to extend.** Reading
`build/cts-work/sweep9.sh` and `build/cts-work/capped.sh`:

- Both pass `--deqp-watchdog=disable` (sweep9.sh:72,116; capped.sh:99), which
  turns the CTS per-case watchdog off entirely. A 30 s (or 90 s) compile
  cannot be killed by it.
- Both invoke `caffeinate -dimsu` with **no `-t`**, so caffeinate does not
  time out; the run lasts as long as glcts does.
- The only watchdog in either script is the **memory** watchdog: a background
  loop every 5 s that kills glcts if total RSS passes ~12 GB
  (sweep9.sh:93-109; capped.sh:71-87). It is unrelated to wall-clock time.
- Neither script sets `ulimit -t` or any per-case alarm.

So a full enhanced_layouts sweep would run to completion with **no script
change**; it simply needs a long wall-clock budget (~17–26 h) and to be left
alone. Two practical requirements it *does* have:

1. **Resumability.** A single ~17 h glcts process is fragile. `sweep9.sh`
   already supports resuming (`$0 <frozen-dir> <starting-case>`, and it
   writes a remainder list). `capped.sh` does **not** — a full run should use
   `sweep9.sh`, or a case list split into chunks.
2. **Keep the watchdog disabled.** Do *not* re-enable `--deqp-watchdog` to
   catch hangs: the default watchdog (~180 s) is shorter than the cumulative
   fp64 compile time of a multi-stage case, so re-enabling it would turn slow
   passes into spurious failures. Accept the small hang risk instead, or cap
   the run with an external `timeout` at the whole-sweep level.

The scripts also already carry the P5.1 change (glcts finds the driver via
rpath; the frozen copy is selected with `DYLD_LIBRARY_PATH` inside
`caffeinate`), so no `MGL_LIBRARY_PATH` handling is needed.

## 5. Recommended approach

**Recommendation: accept the 608-case sample as the published measurement
(option (b)), and take the full run opportunistically as a resumable
background sweep (option (c)) once the per-case cost is measured.**

Reasoning:

- The cache (option (a)) already exists and is correct for fp64, but it cannot
  reduce the dominant cost — distinct shaders per case — so it is **not** the
  mitigation the roadmap hoped for. Do not spend effort here; the only cache
  work worth doing is raising/replacing the 512-entry flush with an LRU so a
  long sweep never recompiles an evicted source (small, low-risk, optional).
- The roadmap already treats the 608-case sample as the stand-in and says so
  in print (line 387). That satisfies P5.3's alternative done-when — *"a
  documented decision that the 608-case sample is sufficient for measurement
  with the reason written in the roadmap"* — provided the reason is recorded.
- The full run is 17 h on the optimistic reading and ~26 h on the realistic
  one, straddling the 24 h done-when. It needs no timeout change, only
  resumability, so it is safe to launch under `sweep9.sh` and let it run;
  but it should not gate the measurement, because the sample already measures
  the same thing.

Concretely:

1. **Measure the real per-case cost first** (see §6) — this decides whether
   the full run is ~17 h or ~26 h, and thus whether it fits the done-when.
2. If ≤ 24 h is confirmed: run the full group once with `sweep9.sh` (resumable,
   watchdog disabled, caffeinate, memory cap), budget 24 h, and publish the
   full figure.
3. If > 24 h is likely: keep the 608-case sample as the measurement, write the
   reason into the roadmap (item 15 / item 29), and run the full group only if
   a long background window exists.
4. Optional hardening: replace the 512-entry full flush with an LRU.

## 6. Specific commands

All paths are relative to the worktree root. GPU-safety first
(`pgrep -lx "llama-server|UTM|glcts|mgl_tests|mgl_probe"`), and only one GPU
job at a time.

**Measure where the 30 s goes, and the true per-case cost** (tools already
exist in `build/cts-work/p53/`, built earlier for this item):

```sh
# Metal's front end vs. pipeline creation vs. recompile, on the captured
# fp64 samples. big.msl is the "large" case; dbl.msl a dmat4 shader;
# plain.msl the same shader with no doubles.
build/cts-work/p53/probe_time build/cts-work/p53/big.msl   2
build/cts-work/p53/probe_time build/cts-work/p53/dbl.msl   2
build/cts-work/p53/probe_time build/cts-work/p53/plain.msl 2

# Command-line metal driver timing, several trials (cold vs warm):
build/cts-work/p53/measure.sh build/cts-work/p53/dbl.msl 3
```

**Prove MGL's in-memory cache is working for fp64** (run the same case twice
back-to-back in one glcts process; the second build of identical MSL should
not pay 30 s). Time a single case, then a two-case list containing the same
case twice, and compare:

```sh
# one fp64-heavy enhanced_layouts case, timed
time submodules/VK-GL-CTS/build/external/openglcts/modules/glcts \
  --deqp-surface-type=fbo --deqp-surface-width=64 --deqp-surface-height=64 \
  --deqp-watchdog=disable \
  --deqp-case=KHR-Single-GL46.enhanced_layouts.<fp64_case>

# the same case twice in one process: list it twice, run under one glcts
printf 'KHR-Single-GL46.enhanced_layouts.<fp64_case>\nKHR-Single-GL46.enhanced_layouts.<fp64_case>\n' > /tmp/twice.txt
time submodules/VK-GL-CTS/build/external/openglcts/modules/glcts \
  --deqp-surface-type=fbo --deqp-surface-width=64 --deqp-surface-height=64 \
  --deqp-watchdog=disable --deqp-caselist-file=/tmp/twice.txt
```

(If the two-case run is barely more than the one-case run, the cache is
hitting; if it is ~2×, the source strings differ — e.g. the two runs emit
different MSL — or the 512-entry flush is intervening.)

**Run the full group, resumably, if the budget allows** (uses the existing
sweep script; no timeout change needed):

```sh
# freeze the driver first, per MEASURE.md
cp build/libmoogl.dylib build/cts-work/frozen-fp64/libmoogl.dylib
# one-case list for the group, then the full resumable sweep
build/cts-work/sweep9.sh build/cts-work/frozen-fp64
# if it is interrupted, resume from the last printed case:
#   build/cts-work/sweep9.sh build/cts-work/frozen-fp64 <last-case-name>
```

**Sanity-check the sample list is the same one used before** (it must be the
fixed 608-case list, not the 180- or 213-case lists):

```sh
grep -c 'enhanced_layouts' build/cts-work/t3s-KHR-Single-GL46.tsv   # 213-list baseline
```

## 7. Uncertainties / left undone

- **No new Metal timings were taken.** The 17 h figure is the roadmap's own
  arithmetic (2,057 × 30 s), not a fresh measurement. The decisive unknown is
  **fp64 shaders per fp64 case**; `probe_time` exists but no output was saved.
  Until that is measured, treat 17 h as optimistic and ~26 h as the
  conservative case.
- The 30 s is quoted for a *shader*; whether it includes
  `newRenderPipelineStateWithDescriptor` (AIR→GPU binary) or only the library
  compile is not stated in the roadmap. `probe_time.m` was written to split
  exactly this and its result is not on disk.
- "608-case sample" is inferred from the roadmap's "one in seven"
  (4,250/7 ≈ 607) and the repeated 608 figure; the literal case-list file for
  it is not in the tree.
- The recommendation assumes the sample's result is accepted for the burndown
  while the full run is still owed for the final submission count (P5.4),
  matching tier item 29 = "half".
