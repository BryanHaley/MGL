## Findings against the specific code the architect asked about

### 1. `src/geometry_shaders.c` — how the geometry rewrite handles TES output

- `mglAddTessGeneralCapture()` (line 2718) is the triangles/quads path: it strips
  `layout(...) in;`, renames `gl_TessCoord`→`mglTC`, `gl_TessLevelOuter`→`mglTLO`,
  `gl_TessLevelInner`→`mglTLI`, `gl_PatchVerticesIn`→`mglPVI`, renames `main`→`mglVsBody`,
  and emits a wrapper `main()` that reads the CPU tessellator's per-patch record out of
  `MglTessGenB` (binding `MGL_TES_GEN_BINDING`), sets `mglTC/mglTLO/mglTLI/mglPVI`, calls
  `mglVsBody()`, then `mglGsCapture()`.
- `mglAddTessPointCapture()` (line 2326) is the isolines path (Metal has no isolines): it
  rewrites the TES as a quad shader and computes the capture slot from `gl_TessLevelOuter`
  and the grid index.
- `MglGsInB` is the generated geometry input buffer; `mglGsCapture()` is emitted at
  `geometry_shaders.c:1883` and only ever writes `mglGsIn[gl_VertexID].mglPos` /
  `.mglPointSize` and the varyings. **It does not write anything to a transform-feedback
  buffer.** That is consistent with case #1: the XFB stream for the tess→geometry path is
  never produced (the buffer stays zeroed).
- The levels the TES body reads come from `mglTLO/mglTLI`, which the wrapper fills from the
  `MglTessGenB` record (`block[1]=inner[0]`, `block[2]=inner[1]`, `block+4=outer[]`). Those
  values were already truncated to fp16 on the way in — see #3.

### 2. `src/tessellator.c` — half-float handling

**There is no half-float code in `tessellator.c` at all.** `grep -i half` matches only the
comment on line 108 ("the far half mirrors the near one"). The tessellator works in `float`
throughout (`MglTessCoord` is `float u,v,w`). The fp16 loss happens *before* it: the
tessellation-factor buffer is a Metal `MTLQuadTessellationFactorsHalf` buffer, and the CPU
reads it back as `__fp16` at `src/MGLRenderer.m:6989`. `mglFloatToHalf`/`mglHalfToFloat` live
in `src/pixel_convert.c:92/133`. So a "half-float fix" for case #3 is **not** in
`tessellator.c`; it is in `MGLRenderer.m`'s level read-back (`tessellateOnCPU:` around
line 6989) or in how the levels are carried to the CPU (keep a full-precision copy rather
than round-tripping through the fp16 factor buffer).

### 3. `src/tessellator.c` lines 120–140 — `innerAtLeastTwo` rounding

```c
static float innerAtLeastTwo(float level, int spacing)
{
    if (level > 1.0f)
        return level;

    return spacing == 2 ? 3.0f : 2.0f;   // 3.0 for fractional-odd, 2.0 otherwise
}
```

This is exactly the code path case #4 (`inner_tessellation_level_rounding`) exercises: inner
level `1.0` with fractional-odd spacing. GL's rule is that an inner level of 1 with a
subdivided outer edge is treated as "1 + epsilon", giving the degenerate marker triangles the
test looks for. Returning a hard `3.0` (or `2.0`) produces the wrong inner ring and the marker
triangle is not found. This function is the primary suspect for #4.

### 4. `src/tessellator.c` `subdivide()` — spacing modes

Lines 78–126. `spacing` is `0=equal`, `1=fractional even`, `2=fractional odd`:

- equal: `n = ceil(f)` clamped to `[1, MAX]`.
- fractional even (case 1): clamp to `[2, MAX]`, `n = ceil(f)`, force even (`n += n&1`).
- fractional odd (case 2): clamp to `[1, MAX-1]`, `n = ceil(f)`, force odd (`n += !(n&1)`).
- default (equal): clamp to `[1, MAX]`, `n = ceil(f)`.

Case #7 reports `expected 29, found 31` for quads/fractional-odd with inner `(32,64)` and
outer `(1,32,1,32)`. The CTS expectation (`esextcTessellationShaderVertexSpacing.cpp:1272`)
is `edge_clamped_rounded - 2*(n_edge/4)` for quads/fractional-odd. A count of 31 vs 29 is the
"two degenerate end segments per edge" that fractional-odd must produce but this `subdivide()`
does not: it cuts `n-2` full segments plus two short ones (lines 107–123) but the
`fractional odd` branch's `n` parity handling and the `even`/`part` split do not reproduce
GL's per-edge segment counts when the outer and inner levels differ. Suspect for #7 is
`subdivide()`'s fractional-odd branch and/or `tessQuads()`'s outer/inner stitching.

## The two link failures are a glslang bug, not MGL

Cases #5 and #6 fail inside `glslang_program_link` (`src/program.c:3604`), which MGL calls to
build the application's own TCS/TES pair before any Metal work. The message names the *same*
type on both sides, which is contradictory. Reproduced standalone with the project's own
glslang build, no MGL involved:

```
$ glslangValidator -l t.tesc t.tese      # tcs: patch out int x[16]; tese: patch in int x[16];
ERROR: Linking tessellation control and tessellation evaluation stages: Array sizes must be compatible:
    tessellation control stage: " int x[16]"
    tessellation evaluation stage: " int x[16]"
```

Root cause is `glslang/MachineIndependent/linkValidate.cpp` `TIntermediate::mergeErrorCheck`
(line 1213) → `isIoResizeArray` (line 2784). For a `patch`-qualified array the control stage's
output is *not* an I/O-resize array, but the evaluation stage's `patch in` input **is**
(`EShLangTessEvaluation && EvqVaryingIn` matches regardless of `patch`), so the two sides take
different branches of the dimension-count comparison and disagree even when the declared sizes
are identical. Any non-empty patch array (N=1,2,3,4,8,16 all fail) triggers it; a scalar patch
variable (`patch out vec4 p`) links fine.

This is upstream glslang behaviour (`isIoResizeArray` and `mergeErrorCheck` are byte-identical
to `KhronosGroup/glslang` main). Options for the architect:
- patch glslang's `isIoResizeArray`/`mergeErrorCheck` to ignore the outer dimension for
  `patch`-qualified arrays, or
- treat the two cases as a waiver (they are a compiler bug in a vendored dependency, not an
  MGL rendering defect).
