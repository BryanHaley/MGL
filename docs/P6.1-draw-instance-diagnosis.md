# P6.1 — the IDKEngine black frame: base instance and draw ID under multi-draw indirect

Diagnosis only. No source under `src/` was changed by this item.

## Summary

The roadmap's standing suspect is *partly* right, but the direction is the
opposite of what the plan assumes, and it is **not** a bug in
`pipeline_draw.c` or `vertex_arrays.c`.

- **`gl_InstanceID` is correct as MGL emits it.** GL's `gl_InstanceID` does
  *not* include `baseInstance`; Metal's `[[instance_id]]` *does*. MGL leaves
  the two mismatched and never applies the `- gl_BaseInstance` correction, so
  under a non-zero base instance every shader that reads `gl_InstanceID`
  gets the Metal value (base-relative), not the GL value (zero-relative).
  The plan's premise ("gl_InstanceID = instance + baseinstance") is wrong; the
  fix is the opposite sign.
- **`gl_DrawID` is not implemented at all.** SPIRV-Cross emits
  `constant uint* spvDrawIndex [[buffer(19)]]` and reads the draw index out of
  Metal buffer slot 19. MGL never binds anything to slot 19, so `gl_DrawID`
  reads whatever garbage (usually 0) is there.
- **The indirect command struct layout is correct** (see §4). The
  `DrawElementsIndirectCommand` in `include/glm_context.h` matches the GL 4.6
  layout, and the offset arithmetic in `MGLRenderer.m` is right.

IDKEngine's GBuffer vertex shader reads both builtins on the very first line
of its geometry work:

```glsl
uint meshInstanceId = visibleMeshInstanceIdSSBO.Ids[gl_BaseInstance + gl_InstanceID];
GpuMesh mesh = meshSSBO.Meshes[gl_DrawID];
```

Both of those indices are wrong for the reasons above, so every mesh is
fetched from the wrong instance and the wrong mesh — a black frame with no GL
error is exactly what that produces.

## 1. What the GL 4.6 specification actually requires

GL 4.6 core, section 11.1.3.9 "Shader Inputs":

- `gl_InstanceID` holds the integer index of the current instance, **starting
  at zero and counting up by one for each instance rendered**. It does *not*
  include `baseInstance`.
- `gl_BaseInstance` holds the integer value passed to `<baseinstance>` (zero
  when the command has no such parameter).
- `gl_DrawID` holds the zero-based index of the draw within a `MultiDraw*`
  command's list; it is zero for a non-`MultiDraw*` command, and it is
  dynamically uniform.

`GL_ARB_base_instance` (the extension that introduced `baseInstance`) settles
the first point in its own issues list:

> **Issue 1) Does `<baseinstance>` offset `gl_InstanceID`?**
> RESOLVED: No. `gl_InstanceID` always starts from zero and counts up by one
> for each instance rendered. If the shader author requires the actual value
> of the instance index, including the base instance, they must pass the base
> instance as a uniform.

`GL_ARB_shader_draw_parameters` says the same thing and explains why:

> `gl_InstanceID` is the integer index of the current instance being
> processed, but, even for commands that accept a `baseInstance` parameter, it
> **does not include the value of this argument**.

Note the plan text quotes "§11.1.3.9: `gl_InstanceID = instance + baseinstance`".
That is not what the section says; it is the Metal (and Vulkan
`gl_InstanceIndex`) rule, not the OpenGL `gl_InstanceID` rule. The
distinction is exactly why the `gl_BaseInstance`/`gl_InstanceIndex` builtins
were added in the first place: an application that wants the absolute index
writes `gl_BaseInstance + gl_InstanceID`.

## 2. What MGL emits

### 2.1 `gl_InstanceID` — missing the base-instance subtraction

The translation is glslang → SPIR-V → SPIRV-Cross MSL. glslang maps
`gl_InstanceID` to the SPIR-V `InstanceId` builtin
(`external/glslang/SPIRV/GlslangToSpv.cpp:822`,
`external/glslang/glslang/MachineIndependent/Initialize.cpp:9175`).

SPIRV-Cross's MSL backend maps `InstanceId`/`InstanceIndex` straight to Metal's
`[[instance_id]]` **unless** `msl_options.enable_base_index_zero` is set
(`submodules/SPIRV-Cross/spirv_msl.cpp:19477-19510`):

```cpp
case BuiltInInstanceIndex:
    if (msl_options.enable_base_index_zero && msl_options.supports_msl_version(1, 1) && ...)
    {
        ...
        ensure_builtin(StorageClassInput, BuiltInBaseInstance);
        return "(gl_InstanceIndex - gl_BaseInstance)";
    }
    else
        return "gl_InstanceIndex";
```

MGL never sets that option. `src/program.c` builds the MSL compiler options
(`src/program.c:1690-1960`) and `SPVC_COMPILER_OPTION_MSL_ENABLE_BASE_INDEX_ZERO`
never appears there — nor anywhere else in `src/`. So the emitted MSL is
`uint gl_InstanceID [[instance_id]]` with no correction.

Metal's `[[instance_id]]`, per Apple's documentation for
`drawIndexedPrimitives(...baseInstance:)`:

> The command assigns each drawing instance a unique `instance_id` value that
> increases from `baseInstance` through `(baseInstance + instanceCount - 1)`.

So Metal's `instance_id` is GL's `gl_BaseInstance + gl_InstanceID`. MGL hands
that value straight to a shader that GL says should see the zero-based
counter. Empirically verified (§3): with `baseIndexZero` off the MSL reads
`gl_InstanceID`; with it on the MSL reads `(gl_InstanceID - gl_BaseInstance)`.

`gl_InstanceID` is therefore **correct only while every draw has
`baseInstance == 0`**. IDKEngine's draw commands do not: `ModelLoader.cs:761`
and `ModelManager.cs:160` set `BaseInstance` to a running offset, and
`ModelManager.cs:223` issues all of them through a single
`glMultiDrawElementsIndirect`. Every instance of every mesh after the first
draw reads the wrong `MeshInstances[]` entry.

(For completeness: `gl_VertexID` has the identical problem with `baseVertex`,
and for the same reason — Metal's `[[vertex_id]]` starts at `baseVertex`.
MGL's MSL emits `gl_VertexID` unmodified, so `gl_VertexID` is also only
correct at `baseVertex == 0`. IDKEngine indexes `vertexPositionsSSBO` with
`gl_VertexID`, so this bites too. This is the same root cause and should be
fixed together.)

### 2.2 `gl_DrawID` — not implemented

glslang maps `gl_DrawID` to the SPIR-V `DrawIndex` builtin
(`GlslangToSpv.cpp:913`). SPIRV-Cross's MSL backend cannot express it
directly, so it **emulates** it: it synthesises a `constant uint*` pointer
named `spvDrawIndex` and reads the draw index from Metal buffer slot
`draw_id_buffer_index`, default **19**
(`spirv_msl.hpp:322`, `spirv_msl.cpp:1097-1106`, `spirv_msl.cpp:17384-17388`):

```cpp
case BuiltInDrawIndex:
    entry_func.fixup_hooks_in.push_back([=]() {
        statement(builtin_type_decl(bi_type), " ", to_expression(var_id), " = *",
                  to_expression(draw_index_buffer_id), ";");
    });
    break;
```

So the emitted MSL entry point carries
`constant uint* spvDrawIndex [[buffer(19)]]` and `gl_DrawID` is
`*spvDrawIndex`.

MGL never binds anything to Metal buffer slot 19:

- the buffer slot constants in `include/glm_context.h` (lines 469-515) name
  slots 0, 21, 22, 24, 27, 28, 29, 30 — never 19;
- `grep -rn "draw_id\|spvDrawIndex\|DrawId" src/` finds no reference to the
  slot at all;
- the only `setVertexBytes:`/`setVertexBuffer:` calls with a fixed index are
  `MGL_CONSTANT_ATTRIB_BUFFER_INDEX` (30), `MGL_BUFFER_SIZES_MSL_SLOT` (21),
  and slot 0.

`gl_DrawID` therefore reads uninitialised Metal buffer contents. Because the
draw-id buffer must be updated per draw *within* a multi-draw (and there is no
per-draw hook in the loop in
`MGLRenderer.m:12299-12349`), this cannot be fixed by binding one buffer once:
each iteration of the loop has to write the current `i` to slot 19 before its
`drawIndexedPrimitives:` call, or the shader needs the value passed another
way.

IDKEngine's GBuffer shader uses `gl_DrawID` as a mesh index and its task
shaders use it as the visible-mesh-instance index, so a zero or garbage
`gl_DrawID` picks the wrong mesh for every draw after the first.

## 3. Empirical evidence (no GPU needed)

The MSL was generated with the project's own glslang and SPIRV-Cross builds.
Input vertex shader:

```glsl
#version 460 core
layout(location = 0) in vec2 pos;
layout(std430, binding = 0) buffer Out { int vals[]; };
void main() {
    vals[0] = gl_InstanceID;
    vals[1] = gl_BaseInstance;
    vals[2] = gl_DrawID;
    gl_Position = vec4(pos, 0.0, 1.0);
}
```

`glslang -V --target-env opengl` then `spirv-cross --msl --msl-version 20100`
(no `enable_base_index_zero`, i.e. MGL's configuration):

```metal
vertex main0_out main0(main0_in in [[stage_in]], constant uint* spvDrawIndex [[buffer(19)]],
                       device Out& _10 [[buffer(0)]],
                       uint gl_InstanceID [[instance_id]], uint gl_BaseInstance [[base_instance]])
{
    uint gl_DrawID = *spvDrawIndex;
    _10.vals[0] = gl_InstanceID;      // <-- GL wants (gl_InstanceID - gl_BaseInstance)
    _10.vals[1] = int(gl_BaseInstance);
    _10.vals[2] = int(gl_DrawID);     // <-- slot 19, which MGL never binds
}
```

With `SPVC_COMPILER_OPTION_MSL_ENABLE_BASE_INDEX_ZERO` set, the same input
produces the correct form:

```metal
    _10.vals[0] = (gl_InstanceID - gl_BaseInstance);
```

`gl_InstanceID` with the option on and `gl_VertexID` with the option on:

```metal
    _10.vals[0] = (gl_VertexID - gl_BaseVertex);
    _10.vals[1] = (gl_InstanceID - gl_BaseInstance);
```

The SPIR-V decorations confirm the builtins involved:
`OpDecorate %gl_InstanceID BuiltIn InstanceId`,
`OpDecorate %gl_DrawID BuiltIn DrawIndex`.

## 4. The indirect command layout is correct

`include/glm_context.h:191-204`:

```c
typedef struct {
    unsigned int  count;
    unsigned int  instanceCount;
    unsigned int  first;
    unsigned int  baseInstance;
} DrawArraysIndirectCommand;

typedef struct {
    unsigned int  count;
    unsigned int  instanceCount;
    unsigned int  first;
    int           baseVertex;
    unsigned int  baseInstance;
} DrawElementsIndirectCommand;
```

This matches GL 4.6 §10.5 / `GL_ARB_base_instance`'s
`DrawElementsIndirectCommand` word for word (`count`, `primCount`,
`firstIndex`, `baseVertex`, `baseInstance`), 5 × 4 bytes = 20 bytes, and the
array variant is 4 × 4 = 16 bytes. The validation in
`src/draw_buffers.c:545-575` (`indirect_error`) uses the right sizes
(`5 * sizeof(GLuint)` / `4 * sizeof(GLuint)`) and the right stride/offset
arithmetic. The renderer's offset arithmetic
(`MGLRenderer.m:12278-12288` and `12333-12346`) is
`(uintptr_t)indirect + i * stride` with `stride == 0` defaulted to the command
size, which is correct.

So the indirect-buffer read path is **not** the bug. The values it passes on
are right; what the shader then does with them is not.

## 5. Where the bugs are, precisely

| # | File / function | Wrong behaviour | Correct behaviour (GL 4.6 §11.1.3.9, ARB_base_instance issue 1) |
|---|---|---|---|
| A | `src/program.c`, MSL option setup (the block at lines 1690-1960, e.g. beside the `SPVC_COMPILER_OPTION_MSL_TEXTURE_1D_AS_2D` set at line 1753) | `SPVC_COMPILER_OPTION_MSL_ENABLE_BASE_INDEX_ZERO` is never set, so the MSL reads Metal's `[[instance_id]]`/`[[vertex_id]]` directly, which start at `baseInstance`/`baseVertex`. | Set `SPVC_COMPILER_OPTION_MSL_ENABLE_BASE_INDEX_ZERO` to `SPVC_TRUE`, so SPIRV-Cross emits `(gl_InstanceID - gl_BaseInstance)` and `(gl_VertexID - gl_BaseVertex)`. |
| B | `src/MGLRenderer.m`, `mtlMultiDrawElementsIndirect` (line 12299) and `mtlMultiDrawArraysIndirect` (line 12250) | `gl_DrawID` resolves to `*spvDrawIndex` at Metal buffer slot 19, which MGL never binds; there is also no per-iteration update, so a single binding could not be right anyway. | Bind a `uint` holding the current draw index `i` to slot 19 before each `drawIndexedPrimitives:`/`drawPrimitives:` call in the loop. GL 4.6 §11.1.3.9: `gl_DrawID` is the zero-based index of the draw within the `MultiDraw*` list, and 0 for a single draw. |
| B′ | same, for the single-draw entry points (`mtlDrawElementsIndirect` line 11947, `mtlDrawArraysIndirect` line 11905, and the plain `draw*` calls) | `gl_DrawID` is undefined/whatever was left in slot 19. | Bind 0 to slot 19 (GL: "In non-MultiDraw* commands, the value of gl_DrawID is always zero"). |

Note for the fix: with `enable_base_index_zero` on, SPIRV-Cross also adds
`[[base_vertex]]`/`[[base_instance]]` parameters, and Metal's `[[base_vertex]]`
/`[[base_instance]]` are the *draw command's* values, so the subtraction is
exactly right for both direct and indirect draws. MGL's draw calls already
pass `baseVertex:`/`baseInstance:` through to Metal correctly for the
non-expanded paths (`MGLRenderer.m:12022`, `12122`, and the indirect paths at
`11914`/`11958`).

## 6. The probe

`tests/probes/probe_draw_instance.c` (new, builds as `build/probe_draw_instance`
via the existing `make probe` rule) draws a quad with a vertex shader that
writes `(gl_DrawID, gl_InstanceID, gl_BaseInstance, gl_VertexID)` into an SSBO
for every invocation, then reads it back and checks it against the spec:

1. `glDrawElementsInstancedBaseInstance`, 3 instances, `baseInstance = 7` —
   expects `gl_InstanceID ∈ {0,1,2}`, `gl_BaseInstance == 7`.
2. `glMultiDrawElementsIndirect`, 2 commands, `baseInstance` 5 and 10 —
   expects draw 0 `gl_DrawID == 0` / `gl_BaseInstance == 5`, draw 1
   `gl_DrawID == 1` / `gl_BaseInstance == 10`, and zero-based
   `gl_InstanceID` in both.

It prints the observed table and exits with the number of expectations not met.
Expected result on the current (frozen) build: case 1 fails on
`gl_InstanceID` (values 7,8,9 instead of 0,1,2); case 2 fails on `gl_DrawID`
(both draws see 0 or garbage) and on `gl_InstanceID`.

The probe has been syntax-checked with
`cc -fsyntax-only -Wall -std=c11 -Iinclude -Iinclude/GL -Itests` and builds
clean; it has **not** been run (this item was diagnosis-only, no GPU run).

## 7. What this means for the plan's "done when"

The plan says "Test fails on frozen (wrong instance ID), passes on new
(correct instance ID)". That is achievable, but note the wrongness is the
*other way round* from the plan's description: the frozen build's
`gl_InstanceID` is base-relative (too large by `baseInstance`), not missing
the base. And the IDKEngine frame needs **both** fixes (A and B) before it can
be non-black, because the GBuffer shader reads `gl_DrawID` as well.
