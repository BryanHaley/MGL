1.  (a) SPIRV-Cross refusing Component on a tessellation interface
----------------------------------------------------------------
FILE:  submodules/SPIRV-Cross/spirv_msl.cpp
FUNC:  CompilerMSL::add_interface_block(StorageClass storage, bool patch)
       starts at line 4532.

The check is at lines 4646-4676, inside the `if (!is_builtin)` branch that runs for each
collected variable:

    4646   // Need to deal specially with DecorationComponent.
    4647   // Multiple variables can alias the same Location ...
    4653   uint32_t component = get_decoration(var_id, DecorationComponent);
    4654   if (component != 0)
    4655   {
    4656       if (is_tessellation_shader() && !msl_options.plain_tessellation_io)
    4657           SPIRV_CROSS_THROW("Component decoration is not supported in tessellation shaders.");
    4658       else if (pack_components)
    4659       {  ... populate meta.location_meta ... }
    4676   }

`pack_components` is set at lines 4544-4548:
    (Input && model==Vertex) || (Output && model==Fragment) ||
    (Output && model==Vertex && capture_output_to_buffer && !plain_tessellation_io)

*** KEY FINDING: this is ALREADY PATCHED in the submodule pointer this worktree carries. ***
`git ls-files -s submodules/SPIRV-Cross` shows pointer 57d00588 ("Tesselation and cull
distance fixes"), which added `msl_options.plain_tessellation_io` (spirv_msl.hpp:564) and
changed pack_components to the form above.  MGL already sets that option:

    src/program.c:1842
        spvc_compiler_options_set_bool(options,
            SPVC_COMPILER_OPTION_MSL_PLAIN_TESSELLATION_IO, SPVC_TRUE);
    (set for VERTEX / TESS_CONTROL / TESS_EVALUATION when ptr->tess.active)

With plain_tessellation_io true the throw at 4657 cannot fire (its guard is
`!plain_tessellation_io`), and pack_components is false for the tessellation vertex
output, so the component is simply carried to the member decoration instead.  The member
decorations are set in two other places, both already carrying Component through:

    spirv_msl.cpp:3121-3124  add_plain_variable_to_interface_block
    spirv_msl.cpp:3933-3936  add_composite_member_variable_to_interface_block

WHAT TO DO:

2.  (b) arrays-of-matrices across a stage interface
----------------------------------------------------------------
FILE:  submodules/SPIRV-Cross/spirv_msl.cpp
There are FOUR throw sites for arrays-of-matrices / arrays-of-arrays, and the fix in
57d00588 landed at only ONE of them:

  3341  CompilerMSL::add_composite_variable_to_interface_block  (line 3321)
        -> FIXED by 57d00588: mat_cols is computed (3328-3349) and the member index is
           split `[i / mat_cols][i % mat_cols]` at line 3488.  elem_cnt is
           array_size * columns.  A single-dimension array-of-matrix where the entry
           point copies the variable in and out now flattens correctly.

  3591  CompilerMSL::add_composite_member_variable_to_interface_block (line 3547)
        -> STILL THROWS.  This is the path taken for a matrix that is a *member of an
           interface block* (block_requires_flattening), and for a struct member that is
           an array of matrices.  elem_cnt = mbr_type.columns and mbr_is_indexable, but
           no mat_cols split - the array dimension is dropped.

  4291  CompilerMSL::add_variable_to_interface_block (line 4208), the block-requires-
        flattening branch -> STILL THROWS.  Same shape as 3591 but for a whole block.

  3734  same function as 3591: "DecorationComponent on matrices and arrays is not
        supported." - a separate, narrower refusal of Component on a matrix/array
        member.

  And the load side: 9617  CompilerMSL::emit_tessellation_io_load (line 9403)
        "Loading array of matrix from IO variable must come directly from IO variable."
        The 9615-9630 branch already reconstructs an array-of-matrix from per-control-
        point data; 9617 is the guard for the case where the pointer is not an IO var.

WHAT TO DO:
  (b1) Extend the 57d00588 mat_cols fix from 3341 into the member path at 3591 and the
       block path at 4291.  In both, when `is_matrix(mbr_type) && is_array(mbr_type)`,
       set `mat_cols = mbr_type.columns; elem_cnt = to_array_size_literal(mbr_type) *
       mbr_type.columns;` and split the member index exactly as 3488 does.
  (b2) Only then relax 3734 if a case still needs Component on such a member.
  VERIFY: cc -fsyntax-only on spirv_msl.cpp, then a GPU test with
          `layout(location=0) flat out mat2x3 m[2];` across vertex->fragment (there is
          already a test for this in tests/gpu/test_varying_layouts.c, see section 6).

NOTE: none of the 15 failing sample cases is an array-of-matrices across an interface
      (the xfb_explicit_location matrix cases are single matrices with an explicit
      location, and the xfb_stride_dvec3 case is a dvec3).  So (b) is on the 608-case
      sample, not on this list.

3.  (c) missing layout validation in MGL
----------------------------------------------------------------
FILE:  src/program.c
There is exactly ONE location-conflict validator today, and it covers *uniforms only*:

  uniformLocationProblem(Program *ptr)          src/program.c:2666
      walks ptr->spirv_resources_list[stage][location_res_types[k]] for
      UNIFORM_CONSTANT / SAMPLED_IMAGE / SEPARATE_IMAGE / STORAGE_IMAGE /
      SEPARATE_SAMPLERS, and returns:
        "link failed: a uniform location is past GL_MAX_UNIFORM_LOCATIONS"   (2684)
        "link failed: two uniforms were given the same location"             (2705)
      It never looks at STAGE_INPUT / STAGE_OUTPUT, and it has no notion of
      Component (the resource struct has no component field - see below).

  Called at src/program.c:4208-4213 (the normal path) and 4084-4089 (the geometry path),
  both AFTER assignUniformLocations(pptr) and only while link_status == GL_TRUE.

Where varying locations are set: assignPipeLocations (src/program.c:2571, forward
declared at :37), called from the MSL emission at 1961/1963 for the vertex and fragment
stages.  It reads explicitLayout(sh->src, name, "location", ...) and packs implicit ones
into the lowest free slot, but it never validates that two explicitly-declared varyings
overlap, and it has no Component at all.

Resource data available: SpirvResource (include/glm_context.h:781) has `location`,
`explicit_location`, `array_size`, `gl_type`, but NO `component` field.  Reflection does
capture it elsewhere - MglResource (include/mgl_reflect.h:66) has `component`, filled in
src/mgl_reflect.cpp:311 from q.layoutComponent - so the raw data exists on the glslang
side and can be read there instead.

WHAT TO DO:
  (c1) Add a new static validator next to uniformLocationProblem, e.g.
           static const char *varyingLocationProblem(Program *ptr);
       For each stage and for STAGE_INPUT / STAGE_OUTPUT, take every resource with
       explicit_location, compute the component span it occupies
       (GL 4.6 section 11.1.3.7: a scalar consumes one component, vecN N, a matrix one
       location per column; two variables may share a location only if their component
       ranges are disjoint), and return
           "link failed: two varyings overlap at the same location and component"
       on any overlap, and
           "link failed: a varying's components run past the end of a location"
       when component + components > 4.
  (c2) Call it from mglLinkProgram right after assignUniformLocations(pptr) at 4206 and
       4208, and in the geometry branch after 4082/4084, in the same
       `if (link_status == GL_TRUE && ...)` shape the uniform check already uses.
  (c3) If per-variable component is needed, either add a `GLint component;` to
       SpirvResource and fill it at src/program.c:2210-2240 from
       spvc_compiler_get_decoration(..., SpvDecorationComponent), or do the whole check
       in src/mgl_reflect.cpp beside mglVaryingLocationsFit (line 731), which already
       walks the glslang linker objects and has the qualifier in hand.

  VERIFY: cc -fsyntax-only -I src -I submodules/SPIRV-Cross src/program.c, then a GPU
          negative test that links a program GL 4.6 requires it to reject (see section 6).
